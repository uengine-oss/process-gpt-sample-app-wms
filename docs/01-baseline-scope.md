# 1.1 기준선: 1차 운영 범위

> 관련 openspec 변경: `supabase-wms-erp-replacement` (task 1.1)
> 이 저장소(`process-gpt-sample-app-wms`)는 ProcessGPT의 **샘플/데모 애플리케이션**이다.
> proposal.md는 "물류학과 실습과 실제 기업 적용 모두를 지원"을 목표로 명시하므로,
> 1차 범위는 실제 고객사 규모가 아니라 **BPMN 전체 흐름(부족 감지→RFQ→HITL 승인→PO→입고→검수→폐기/적치)을
> 처음부터 끝까지 End-to-End로 증명하는 데 필요한 최소 규모**로 정한다.
> design.md §16의 수치(테넌트당 100창고, SKU 100,000, 연 1,000만 원장 entry 등)는
> 실제 고객 적용 시 재확정할 상한 목표로 남겨두고, 아래는 이 샘플 앱의 데모 기준선이다.

## 1차 운영 범위 (데모 기준선)

| 항목 | 값 | 근거 |
|---|---|---|
| 테넌트 수 | 2 (데모 테넌트 A/B, 테넌트 격리 시연용) | RLS 교차 테넌트 차단을 실제로 보여주려면 최소 2개 필요 |
| 창고 수 | 테넌트당 1~2개 (총 2~3개) | 존/로케이션/도크 기준정보 데모에 충분 |
| 상품(SKU) 수 | 창고당 20~50개 | 재보충·FEFO/FIFO·lot 시나리오를 다양화할 최소 표본 |
| 공급사 수 | 3~5개 | RFQ 견적 비교 시연에 필요한 최소 복수 견적 |
| 동시 사용자(모바일 현장) | 5명 이하 (부하 테스트는 별도 acceptance 단계) | task 11.6에서 별도 부하 테스트로 검증 |
| 재고 원장 entry (연간 추정) | 10,000건 이하 | 데모/실습 규모 |
| 가용성 목표 | 데모 환경 기준 별도 SLA 없음 (Supabase 표준 가용성 의존) | 프로덕션 SLA는 실제 고객 적용 시 별도 확정 |

## BPMN 대상 프로세스

첨부 BPMN(재고 부족 감지 → 재고/수요 확인 → 재보충 판단·RFQ → 구매 승인(HITL) →
PO 확정 → 공급사 통지 → 하역장 접수 → 입고 검수 → 폐기/반품/재작업 또는 적치)
전체가 이 샘플 앱만으로 Odoo 없이 실행되어야 한다. (design.md §1, §3 목표와 동일)

## 제외 범위 (데모 기준)

design.md §3 "제외 범위"를 그대로 따른다: 총계정원장/세무/급여/CRM/제조 MRP 전체,
TMS 배차 최적화, 자동창고 PLC/WCS 저수준 제어, 수요예측 ML, 범용 BPM 재구현.
추가로 샘플 앱 단계에서는 다음도 1차 스코프에서 제외한다.

- Odoo 실 데이터 이관(11.3~11.5): 샘플 앱은 그린필드로 시작하므로 이관 리허설은
  이 저장소가 아니라 별도 운영 문서로 다룬다. 데모에서는 시드 데이터로 대체한다.
- 다국어 UI. 1차는 한국어 UI로 시연한다.

## 승인 필요 사항

이 기준선은 데모 목적의 기본값이며, 실제 고객 적용 시 아래 항목은 이해관계자 재확인이 필요하다
(design.md §19 "열린 질문"과 동일):

- 재고평가 방식(이동평균/FIFO/표준원가)
- 공급사 협업 채널(이메일 vs 포털)
- 출고 주문 원천 우선순위
- 냉장/위험물/유통기한 규칙 적용 창고 범위
- 전자세금계산서/회계 전표 소유 여부
